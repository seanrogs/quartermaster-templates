# Build gang template

Populates an N26 `.qmtemplate` file (fighters, equipment catalogue, skills) from photographed rulebook pages, and keeps `N26/REVIEW_NOTES.md` updated with every judgment call made along the way. This is a multi-turn process — screenshots typically arrive one page/table at a time across a conversation, not all at once.

All edits are done as targeted text/line insertions into the plist XML, never a full `plistlib` rewrite of the whole file — `plistlib.dump` reformats every existing `<real>`, and produces a huge spurious diff. Only use `plistlib.load` (read-only) for lookups and for validating a file after editing it.

**Real-number formatting, confirmed against what the Quartermaster app itself writes**: a zero `Points` value is always `<real>0.0</real>` (never bare `<real>0</real>`) — this is the one case where the trailing `.0` is required; nonzero whole-number values stay bare (`<real>20</real>`, not `20.0`).

**Gang name capitalization**: whenever a gang's own name would otherwise appear lowercase in a `Name` or description (e.g. a mount named after the gang), title-case just that word — `Escher cutter`, `Goliath mauler` — while the rest of the name stays lowercase, matching the project's general lowercase-common-noun convention for equipment names.

## 0. Setting up a new gang file

1. Find the original, pre-work skeleton of an existing gang file in git history (e.g. `git log --follow -- "N26/House Cawdor.qmtemplate"`, take the earliest commit) and pull it: `git show <sha>:"N26/House Cawdor.qmtemplate" > "N26/House <NewGang>.qmtemplate"`.
2. If that skeleton contains an example fighter (a hand-authored template fighter left in by the user), strip it out so the new file starts with genuinely empty `Units` arrays for every Organisation class — don't carry another gang's named fighter into the new file. Convert its parent `<array>...</array>` to a self-closed `<array/>`, and delete the whole unit `<dict>...</dict>` between them (watch for an off-by-one: the deletion range is `[array_open+1 : dict_close+1]` inclusive of the unit's own closing `</dict>`, and don't forget to remove the now-orphaned `</array>` that closed the original array — validate with `plistlib.load` immediately after and fix indentation-only mismatches if the parser complains about a mismatched tag).
3. Rename `<key>Army List Name</key>`'s `<string>` to the new gang's name.
4. Validate with `plistlib.load` before moving on. Log the "did I keep or strip the example fighter" decision (and why) as the first entry for this gang in `N26/REVIEW_NOTES.md`.

## 1. Recognizing what a screenshot is

- **Fighter stat card** (name banner, credit cost, M/WS/BS/S/T/W/I/A/Sv and Ld/Cl/Wil/Int rows, a "Type" cell, "Starting XP") → §2.
- **Equipment price list** (section headers like RANGED WEAPONS / CLOSE COMBAT WEAPONS / WARGEAR, item name + "... N credits", sometimes a faction-restriction parenthetical) → §3.
- **Equipment stat reference** (SR/LR/Str/AP/L/Traits columns plus Creds/TP, grouped under the same section headers) → §3, paired with the price list.
- **Skill access table** (fighter names down the left, Agility/Brawn/Combat/Cunning/Savant/Shooting/etc. across the top, cells are Primary/Secondary/–) → §4.

## 2. Fighter roster

Capture: **Name, Points (credits), Stats (the M/WS/.../Sv•Ld/Cl/Wil/Int line joined with `•`, same bullet format as `N26.qmsystem`), Special Rules (the literal "Type" cell text, e.g. `Fighter (Champion, Pious)`), XP (Starting XP)** — plus, where the card gives them, the fighter's own **starting skill**, **named special rule**, and **fixed/included starting equipment** (see below). Multi-sentence custom mechanics that don't reduce to a short name or a fixed weapon (Wyrd power selection, an activated action with several steps, a condition-inflicting attack sequence) still aren't modeled — flag those skips in the review notes.

**Starting skills and named special rules → append to `Special Rules`.** If a card has a line like "Skills: A `<Fighter>` has the `<Skill>` skill" or a bolded named ability (e.g. "Rule of Iron", "Combat Chems Stash", "Regeneration", "From the Shadows"), append `; <Name>` to the fighter's `Special Rules` string (just the bolded title, not the full rule text) — e.g. `Fighter (Prospect); Dodge`, `Fighter (Champion); Rule of Iron`. Multiple additions are comma-joined after the one semicolon (`Fighter (Beast, Pet); Leash Range 3", Clamber, Fearsome`). A fighter whose card has no such line gets no addition — don't invent one.

**Fixed/included starting equipment → an `Equipment` key on the fighter.** If a card says a fighter "is equipped with `<X>` (included in their cost)" or is simply "armed with `<X>`" with no purchase choice, add an `Equipment` key (alphabetically between `Command` and `Magic`) shaped like a Pet's: an array of `<array><dict>...</dict></array>` slots, each dict `Count:1, Default:true, Maximum:1, Name, Points:0.0, Special Rules, Stats` (weapon stats/traits from the equipment reference page; omit Special Rules/Stats for a non-weapon item like a jump booster). If the card also offers a swap or an independent add-on for credits (e.g. "may replace X with Y ... +N credits", "may take Z ... +N credits"), add it as a sibling dict in the same slot array (`Count:0, Name, Points:<cost>`, no `Default`) for a *replacement* choice, or as its own separate one-dict slot array for an *independent optional* purchase that isn't mutually exclusive with anything else. Get the swap/add-on's `Points` from the card's own "+N credits" text — don't leave it at 0.

**Role mapping** from the Type string: starts with "Vehicle" (not "Fighter") → the Organisation's `Vehicle` class, built the same way as any other unit (same tail schema, gets pets attached like everyone else); else contains "Pet" → not a roster role at all, see **Pets** below; else contains "Leader" → Leader; "Champion" → Champion; "Brute" → Brute; anything else (Ganger, Prospect, plain Beast, etc.) → Fighter, the default bucket.

**Pets — always an attached unit, never standalone.** A fighter whose Type includes "Pet" (e.g. `Fighter (Beast, Pet)`, `Fighter (Beast, Flying, Pet)`) is *never* added to a Organisation class's `Units` array on its own, even when the rulebook gives it a full priced card with its own stat block — that's just how the book presents it, not how the data model represents it. It must instead become an entry in every other fighter's `Attached Units` array, the same way Cawdor's Sheen Bird works. (A Beast that's a **Brute**, not tagged Pet — e.g. Khimerix, Piscean Spektor — *is* a standalone roster fighter in the Brute role; only the Pet tag triggers this treatment.) If a gang has more than one pet type, all of them go into the same shared `Attached Units` array, applied identically to every other fighter (don't pick one).

**Building a pet's Attached Units dict** (do this once per pet type, reuse for every fighter): take an existing pet dict from this file (or Cawdor's Sheen Bird, the original reference) as the template, from its `<dict>` through matching `</dict>`. Its shape: `Command` (the same Advancements/Lasting Injuries boilerplate as a regular fighter), then `Equipment` (an array of sibling `<array><dict>...</dict></array>` entries, one per innate weapon the pet's card says it's "armed with" — most pets have exactly one, but some have two, e.g. a beast with both a bite and a ranged natural weapon; each is a `Count:1, Default:true, Maximum:1` entry with name/Special Rules/Stats from the "Natural Weapons" (or relevant ranged) section of the equipment reference page), then `Magic` (a single `Skills` dict — same shape as a fighter's own Skills entry, but not nested under `Advancements`), then a tail of `Maximum Size`/`Minimum Size`/`Name`/`Points`/`Size`/`Special Rules`/`Stats`/`XP` (**no `Upper Limit`**, unlike a top-level fighter's tail). For `Special Rules`, follow Sheen Bird's pattern: the Type string plus a semicolon-joined short summary of any one-line keyword rules (e.g. `Fighter (Beast, Pet); Leash Range 3"`) — skip multi-sentence custom rules (Regeneration, Sensor Array, etc.), same as for fighters generally.

**`Upper Limit` is Leader-only.** Every other role (Champion, Fighter, Brute, Vehicle) omits the `Upper Limit` key from its tail entirely — a gang can field more than one Champion/Ganger/etc., just not more than one Leader. Don't include the key-value pair at all for non-Leaders (not even `-1`).

**Brutes — and any other unit whose card explicitly says it "may not purchase or be equipped with additional weapons or wargear"** (this wording sometimes shows up on a Vehicle too, e.g. a walker's own card) — lose their general purchasing ability and their pet option, and gain their card's weapons as fixed `Equipment` instead:
- Remove the fighter's own top-level `Magic Items` key (the equipment-category purchase list) entirely.
- Remove `Attached Units` entirely — a restricted unit doesn't get the gang's pet(s) attached, even though every other fighter does.
- Add an `Equipment` key (see the "Fixed/included starting equipment" rule above) built from the card's own weapon(s) and any swap/add-on options it lists — this is how the unit gets weapons at all, since it can't buy any.
- `Command` and `Magic` (its skill-access entry) stay untouched — a Brute still advances and still has skill access, it just can't shop.

**Building the unit block:**
1. Locate an already-built fighter in this same file (or, for the very first fighter, hand-author one) to use as the boilerplate template — it carries the full `Command` → `Advancements`/`Lasting Injuries`/equipment-category `Magic Items` tree that every fighter shares verbatim, and (if this gang has pets) the `Attached Units` block too. Extract it as raw lines: from the unit's opening `<dict>` through the last shared line before the fighter-specific tail (`Maximum Size`/`Minimum Size`/`Name`/`Points`/`Size`/`Special Rules`/`Stats`/`XP` for non-Leaders, or that plus `Upper Limit` for a Leader, alphabetical key order, ending `</dict>`).
2. Generate the tail per fighter (5-tab-indented keys under a 4-tab `<dict>`/`</dict>`, matching the template's own indentation) and append to the template lines.
3. Insert into the matching Organisation class's `Units` array (find the `<string>ClassName</string>` under `Organisation`, then its `<key>Units</key>`, then the array — convert `<array/>` to `<array>...</array>` if this is the first unit in that class, otherwise insert before the existing `</array>`).
4. Apply the Brute-restriction removals (above) and any Equipment/Mount additions afterward, per-fighter.
5. Validate the whole file with `plistlib.load` after each batch, and spot check a couple of fighters' full structure (`Attached Units` present with every pet type except on restricted units, tail fields correct, no stray `Upper Limit` on non-Leaders).

## Mounts

A mount either (a) just grants a subtype and sets Movement, or (b) also comes with its own weapon(s). Tell them apart from the mount's own rules-reference text.

**(a) Subtype/movement only** (e.g. Dirt Bike, Van Saar's Grav Cutter): add `Special Rules` (comma-joined subtypes, e.g. `Mounted`, `Mounted, Agile, Flying`) and `Stats: "M=<value>\""` directly to the mount's entry in the gang's `Items` → Mounts catalogue — it stays a normal purchasable item, no per-fighter structure needed.

**(b) Grants its own weapon(s)** (e.g. Escher Cutter, Goliath Mauler, Orlock's Outrider Quad): remove it from the `Items` → Mounts catalogue entirely — it's no longer a plain purchase — and instead add a `Mount` key (alphabetically between `Minimum Size` and `Name`) to every fighter who isn't restricted (see Brutes above; a restricted unit doesn't get this either). Shape: `Mount` → array → array → one dict: `Count:0, Maximum:1, Name` (gang-name-titlecased per the capitalization rule), `Options` (see below), `Points` (the mount's cost), `Special Rules`/`Stats` (its subtype/movement grant, same as case (a)). `Options` is an array of independent "slot" arrays — one slot per weapon-choice group: the primary weapon slot holds the default weapon (`Count:1, Default:true, Maximum:1`) alongside any swap alternatives (`Count:0`, `Points` = the swap's own "+N credits"); a bundled sub-ammo option that depends on keeping the default weapon becomes its own slot with `Prerequisite: [<default weapon's Name>]`. Nested weapon option names follow the same gang-name-style capitalization as the mount itself (e.g. `Mauler boltguns`, `Cutter heavy stubbers` — the brand-prefix word capitalized, the rest lowercase), unlike ordinary catalogue weapons which stay all-lowercase.

**A mount included in one specific fighter's starting cost** (e.g. "equipped with a Grav Cutter (included in their cost)") gets a `Mount` key too, but the simple included-item shape instead: `Count:1, Default:true, Maximum:1, Name, Points:0.0, Special Rules, Stats` — no `Options`, since there's no purchase choice involved, just a free copy of the case-(a)-style mount.

## 3. Equipment list + reference

Target is the gang's own `Items` array (9 categories: Ranged Weapons, Close Combat Weapons, Grenades, Armour, Field Armour, Personal Equipment, Gang Equipment, Weapon Accessories, Mounts) — distinct from `N26.qmsystem`'s master catalogue, which is only a lookup source here.

For each priced line in the equipment list:
1. **Look it up by exact name** (case-insensitive) in the matching category of `N26.qmsystem`.
2. **Match found** → deep-copy that item, strip only a `TP N` segment from its `Prerequisite` (keep any other comma-separated segment, e.g. a parent-weapon reference), and override `Points` if the gang's list price differs from the master catalogue.
3. **No match** → check if the equipment-list line actually *names a bundle of items that individually exist in N26* (e.g. `sawn-off shotgun with solid & scatter shot` bundling `sawn-off shotgun scatter shot` + `sawn-off shotgun solid shot`, or `grenade launcher with frag & krak grenades (+smoke sub-option)` bundling three grenade-launcher ammo entries). If so, split it into its matched components rather than adding one bare stub — this reads far better than a single opaque line, and matches what's already in the file for Cawdor/Delaque.
4. **Genuinely new** (not in N26 at all, and not a bundle of things that are) → add a bare entry with only `Category`/`Name`/`Points`. If the equipment-*reference* page (stats/traits) for this item is available in the same batch, add `Special Rules`/`Stats` too instead of leaving a stub — don't make the user come back for a second pass if the data's already in hand. If only the reference page arrives later, fill the stub in then.
5. **Restriction tags**: if an item is exclusive to one sub-list (e.g. a gang vs. its allied cult, like Cawdor/Redemptionist), one specific named fighter (e.g. "Psy-Gheist only" → `Psy-Gheist`), or one specialist sub-role (e.g. "Gunner specialist only" → `Gunner specialist`, keeping the word "specialist" since it's a role restriction rather than a proper name), add `Prerequisite: [<bare tag>]` — drop "only"/"exclusive" wording either way, and don't leave the restriction sitting in the item's `Name` in parentheses (e.g. `exterminator (autogun, shotgun, chainaxe and eviscerator only)` should be `Name: exterminator`, `Prerequisite: [autogun/shotgun/chainaxe/eviscerator, Redemptionist]` — a slash-joined list folded into the Prerequisite string, not the display name). If the item already has a kept non-TP prerequisite segment, join with a comma (`<existing>, <tag>`). If the *same* item name appears in two sub-lists at *different* prices, it can't be one shared entry — add it twice, once per tag, rather than picking one price.
6. **Ammo-type variants get `Multiple: true` and a parent-weapon reference in their Prerequisite**, even brand-new ones with no N26 match (e.g. a new `<weapon> executioner ammo` sub-item should carry `Prerequisite: [<weapon>, <tag>]` and `Multiple: true`, matching how `sawn-off shotgun solid shot` etc. already work) — don't leave a bare faction/fighter tag with no weapon reference on an ammo item, and don't omit `Multiple` just because the item is new.
7. **Skip, don't stub**: items with no independent credit cost that only exist as another fighter's built-in loadout or swap option (e.g. a Brute's default weapon, or an upgrade only reachable through one specific fighter's equipment text) — these aren't equipment-list purchases. Log the skip.
8. Shared items (same name, same price, in every relevant sub-list) get no restriction tag at all.
9. **Dual-profile weapons** (a melee base with a bolted-on ranged attachment, e.g. Cawdor's polearms; a lance that's a different Stats/Special Rules while "primed" vs. "spent") split the same way as bundled items: the item already in the catalogue keeps its existing name and becomes the primary/melee profile, and each additional profile becomes a `Points: 0.0` sub-entry named `<parent> <component>` with `Prerequisite: [<parent>, <tag>]`. For a state-change weapon (primed/spent), only model the primed (full-power) profile — the spent downgrade is a battlefield mechanic, not a separate purchase, and isn't captured.

Always validate with `plistlib.load` and spot-check a few entries (especially any split/renamed bundles) after each batch.

**Stash needs a `Gang Equipment` allowance.** Every gang's Campaign class has a fixed `Stash` unit with its own `Magic Items` purchase-category list (Weapons/Weapon Accessories/Grenades/Armour/Field Armour/Personal Equipment/Mounts) — this list is missing `Gang Equipment` by default (a leftover from the original skeleton) and needs it inserted between `Personal Equipment` and `Mounts`, once per gang file. This is a Stash-only fix — individual fighters' own `Magic Items` lists don't include `Gang Equipment` and shouldn't.

## 4. Skill access table

Maps each fighter to 0+ `(SkillSet, Primary|Secondary)` pairs. Locate, for each fighter, the *fighter's own* `Skills` advancement dict (`Name: "Skills"`, `Maximum: 1`) inside their `Command` tree — not the attached companion's, if this gang has one (search backward from the fighter's `Name` line for the nearest preceding `<string>Skills</string>`; the companion's copy, if any, is always further back). Replace its `Magic Items` array entirely with dicts of the form `{Items: [], Limit: -1, Name: "<SkillSet> Skills", Prerequisite: "Primary"|"Secondary"}`, in the table's column order. A fighter listed in the table with every column dashed still keeps an (empty) entry only if the table explicitly lists them — if a roster fighter is *absent from the table entirely*, remove their `Skills` dict from `Advancements` → `Options` rather than leaving it empty.

**Skewed photos**: these tables are frequently photographed at an angle that makes column alignment genuinely unreliable to OCR — don't guess a full table from a skewed image. Read what's confidently legible, and either ask the user to confirm/correct specific ambiguous cells (via a short targeted question, not a full re-ask) or, if more than a couple of cells are unclear, ask the user to write the table out directly rather than guessing twice.

## 5. Review notes

After finishing a batch of work (a fighter roster, an equipment list, a skills pass), append to `N26/REVIEW_NOTES.md` under that gang's `##` section (create the section if it doesn't exist yet). Log: naming/splitting decisions for bundled or ambiguous items, anything skipped and why, restriction-tag choices, cost conflicts between sub-lists, and any table cells that needed the user's confirmation. Keep entries terse — one or two sentences each, grouped by theme, not a chronological transcript.
